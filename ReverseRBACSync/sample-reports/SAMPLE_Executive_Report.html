Executive Summary

The Business Problem

Acme Demo manages Kubernetes RBAC through their identity provider (IdP) integration, ensuring consistent access control across their 2 clusters. However, Komodor currently has no mapping between the IdP groups and Komodor policies, creating a "permission drift" risk where Komodor access may not match their actual K8s permissions.

  • Existing Komodor policies are generic rather than group-specific (see Current State)

Recommendation

Create 6 group-specific Komodor policies that mirror the existing K8s RBAC structure. This will ensure users have appropriate Komodor access matching their Kubernetes permissions, eliminating permission drift and maintaining consistency with their IAM-managed access model.

Request Background

Acme Demo requested a "Reverse RBAC Sync" solution to address their concern about permission drift. Instead of using Komodor as the source of truth for RBAC (which would require manual configuration), they want Komodor to automatically read and mirror their existing Kubernetes RBAC configuration.

Why "Reverse RBAC Sync"?

Traditional RBAC sync pushes Komodor policies to Kubernetes. This approach reverses it:

  • Source of Truth: Kubernetes RBAC (managed via the IdP/IAM integration)
  • Target: Komodor policies (automatically generated from K8s)
  • Benefit: No manual configuration needed, always in sync with IAM

Goal

Automatically align Komodor user permissions with their Kubernetes RBAC permissions, ensuring that when users log into Komodor via SAML, they receive access that matches their existing K8s permissions without any manual policy configuration.

Understanding Kubernetes RBAC

Kubernetes RBAC uses five key resource types to define and assign permissions. Here's how they work, with illustrative examples:

ClusterRole - Permission Template

Defines WHAT permissions exist. A ClusterRole specifies verbs (actions like get, list, watch, create, update, delete) and resources (like pods, deployments, secrets) that can be accessed.

Example: "platform-readonly" ClusterRole
- Verbs: get, list, watch (read-only)
- Resources: * (all resources)
- Result: Read-only access to everything in the cluster

ClusterRoleBinding - Links Roles to Groups

Defines WHO has cluster-wide permissions. A ClusterRoleBinding connects a ClusterRole to subjects (users, groups, or service accounts).

Example: ClusterRoleBinding "platform-team-binding"
- ClusterRole: "platform-readonly"
- Subject: Group "platform-team"
- Result: All members of the "platform-team" identity group get read-only access cluster-wide

Role - Namespace-Scoped Permission Template

Same as ClusterRole but limited to a specific namespace. Defines permissions that only apply within that namespace.

Example: Role "app-team-editor" in namespace "payments"
- Verbs: get, list, watch, create, update
- Resources: pods, deployments, services
- Result: Read/write access to pods, deployments, and services, but only in the "payments" namespace

RoleBinding - Links Roles to Groups in Namespace

Connects a Role to subjects within a specific namespace. Users/groups get the Role's permissions only in that namespace.

Example: RoleBinding in namespace "payments"
- Role: "app-team-editor"
- Subject: Group "app-team"
- Result: Members of "app-team" group can manage resources in the "payments" namespace only

ServiceAccount - Machine Identities

Service accounts are used by pods and automation tools, not human users. They're not relevant for mapping identity groups to Komodor policies (which is for human users).

How We Analyzed the RBAC

We scanned all ClusterRoleBindings and RoleBindings to find which identity groups are bound to which roles. Then we examined the ClusterRoles and Roles to understand what permissions those groups have. Finally, we mapped those K8s permissions to Komodor actions to generate matching policies.

  • Permission drift occurs when K8s RBAC changes but Komodor doesn't

Remaining Gaps and Limitations

No Automatic Sync Capability

Currently, this is a one-time analysis. If K8s RBAC changes (new groups, modified permissions), the pipeline must be re-run manually. A future product feature could provide continuous automatic sync.

Komodor-Specific Actions Require Manual Decision

Actions like exec:pod, manage:klaudia, Helm management, and user administration don't have K8s RBAC equivalents. These must be manually added to policies based on business requirements.

ServiceAccount Permissions Not Mapped

ServiceAccount bindings were analyzed but not included in policy generation, as they represent machine identities rather than human user access.

Custom Resources May Have Limited Support

Some Kubernetes Custom Resource Definitions (CRDs) may not have direct Komodor action equivalents. These are mapped to view:custom-resource or edit:custom-resource where possible.

Pod Subresources Are Not Auto-Mapped

K8s grants exec, port-forward, log access, and scale via subresources (e.g., pods/exec, deployments/scale). The mapper matches base resources only, so actions like exec:pod and forward:port are never granted automatically and must be added to policies manually where appropriate.

Rule Granularity Caveats

resourceNames restrictions in K8s rules are not carried over (the generated grant covers the whole resource type in scope), and wildcard rules (resources: ["*"]) map to the full set of Komodor view/edit/delete actions, including some platform-level view actions. Review generated policies before applying.
